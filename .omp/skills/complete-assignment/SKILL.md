# Complete Assignment - 结构化作业完成流程

用户以固定模板（`Complete-assignment-thoroughly:` 等）指派批量作业时使用。作业通常包含：**仅这些文件** 的目标清单、**待核实与修复项** 列表、以及明确的接受条件。目标是一次通过、不留半成品。

## 触发条件

- 请求含 `Complete-assignment`、`Complete assignment`、`thoroughly`、`仅这些文件`、`待核实与修复项` 等固定模板特征
- 用户列出多个目标文件 + 明确的修复/核实条目清单
- 作业要求在限定文件集内完成并验收

## 流程（四步）

### 1. 解析目标与边界

- 逐条读取作业的 `Target` 文件清单，确认**只**改动列出的文件（除非验收条件明确要求连带修改）
- 读取每条 `待核实与修复项`，区分：可立即修复项 / 需先核实再修复项 / 无法在当前环境复现项
- 若某项含糊（缺少复现步骤、指向不存在的符号），先向用户确认，**不要猜测后动手**

### 2. 核实（对需核实的条目）

- 定位条目指向的源码/测试/配置，读取实际内容，确认问题是否真实存在
- 对"疑似 bug"：先复现（跑最小测试/脚本），确认根因后再改
- 记录核实结论：`确认存在 → 修复` / `无法复现 → 说明原因并标记待确认`

### 3. 实现或修复

- 只改目标文件；同文件的写入串行执行
- 修改前先读取文件当前内容（避免基于过时快照编辑）
- 遵守项目硬规则（`.omp/RULES.md`）：事务、权限、覆盖率、Python 版本、并发安全

### 4. 验证与验收

- 对每个改动条目跑**相关验证**（该文件的测试/lint/类型检查），不要只跑无关的全局套件
- 汇总验收表：每条目标 → 改动 → 验证命令 → 结果（通过/失败）
- 若验证失败：诊断 → 修复 → 重验（失败 → 编辑 → 重跑，直到通过）
- 交付时写明「验收边界 + 最终验证结果」（见 `.omp/RULES.md` 可靠交付规则）

## 输出格式

```
## 完成摘要
- 目标文件: N 个（列出）
- 已修复: M 条 / 已核实无需修复: K 条 / 待确认: X 条

## 逐项验收
| # | 条目 | 改动 | 验证 | 结果 |
|---|------|------|------|------|

## 备注
- 无法核实/无法复现的条目及原因
```

## 边界

- **不做清单之外的工作**：不要顺手重构、加测试、修无关 bug（除非验收条件明确要求）
- **不跳过核实**：对"待核实"条目，未经核实不得直接宣称已修复
- **不以偏概全**：一个文件的改动不要扩大成全局改动
