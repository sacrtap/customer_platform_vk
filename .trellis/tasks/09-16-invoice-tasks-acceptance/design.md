# 验收方法设计

## 1. 验收策略：三层取证

| 层 | 手段 | 适用 AC | 成本 |
|---|---|---|---|
| L1 静态核对 | 读实现代码确认路径存在 | 全部（**已在本任务 prd.md Background 完成**） | 最低 |
| L2 接口层 | `curl` / Python 脚本直接调后端 API，断言响应 | 后端行为类：状态流转、字段透传、金额计算、下载、重试 | 低 |
| L3 UI 实跑 | 浏览器打开 `localhost:5173` 操作并断言 DOM/网络 | 纯前端行为类：周期保留、自动刷新、列渲染、文案 | 中 |

**原则**：能用 L2 证明的**不**用 L3。L1 只能证明「代码存在」，**不能**作为 AC 通过的证据 —— 每个 AC 至少需要 L2 或 L3 的运行时证据。

## 2. 证据类型与留存格式

所有证据写入本任务 `implement.md` 的验收结果表，格式：`AC 编号 | 结论 | 证据（命令 + 关键输出）| 层级`。

- **L2 证据**：执行的命令 + 响应关键字段值（如 `detail_file_status: completed`、`final_amount: 1234.56`）。
- **L3 证据**：操作序列 + DOM/网络请求断言结论（浏览器证据以断言为主，不强制截图）。
- **副作用登记**：本次创建的结算单 ID、生成的 Excel 路径、上传的附件路径，全部登记以便清理。
- **Excel 取证**：用 `openpyxl` 读取生成的文件，输出 Sheet 名列表、明细表头（应 29 列）、数据行数；并与外部库同条件 `COUNT(*)` 对比。

## 3. 环境与凭据（已实测）

- 后端 `http://localhost:8000`（Sanic）、前端 `http://localhost:5173`（vite）、PostgreSQL 5432、Redis 6379 均在运行。
- 外部 MySQL 可达（`nest_model_order` 4,663,269 行）。
- 登录：`POST /api/v1/auth/login`，`admin` / `admin123` → `code: 0`。

## 4. 验收顺序

1. **`09-03` 先验**（成本低、无副作用）：AC9 用 L2；AC1/AC2/AC3/AC10 用 L3；AC4–AC8 用 L3（需构造不同计费类型的客户）。
2. **`09-02` 后验**（有写库副作用）：AC1b/AC1c/AC1d/AC5/AC6/AC7 用 L2；AC1/AC2/AC3/AC4 用 L2 + Excel 读取。

## 5. 数据构造

- `09-03` 的 AC4–AC8 需要**四种计费类型各一个客户**。优先复用已有客户（按其 `pricing_type` 筛选）；若某类型缺失，记录为「无法验证」并说明，不擅自新建生产数据。
- `09-02` 的 AC1 需要一个**有已确认消费数据、且能匹配外部库 `group_type`** 的客户，才能在明细 Sheet 中产生数据行。选型依据：`invoice_excel.py` 的 `DETAIL_SQL` 按 `group_type` + `upload_date` 区间过滤。

## 6. 风险控制

1. **写库副作用**：创建的结算单保持可识别（如选定一个固定测试客户 + 明确周期），ID 登记在案，验收结束后向用户汇报以便清理；**不擅自删除**生产/开发库记录。
2. **异步等待**：`detail_file_status` 走 `pending → generating → completed/failed`，需轮询（建议 2 秒间隔、最多 60 秒），超时记为「无法验证」而非「不通过」。
3. **外部库只读**：验收只执行 `SELECT`，绝不写外部库。
4. **修复原则**：判「不通过」时在本任务内修复，但改动限于使该 AC 成立的最小集；修复后重跑受影响 AC + 相关既有测试（`tests/integration/test_billing_import_export_api.py`、`tests/test_repository/` 等）。
